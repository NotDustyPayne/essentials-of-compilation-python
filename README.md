# python-student-support-code

Support code for students (Python version).

The `runtime.c` file needs to be compiled by doing the following
```
   gcc -c -g -std=c99 runtime.c
```
This will produce a file named `runtime.o`. The -g flag is to tell the
compiler to produce debug information that you may need to use
the gdb (or lldb) debugger.

On a Mac with an M1 (ARM) processor, use the `-arch x86_64` flag to
compile the runtime:
```
   gcc -c -g -std=c99 -arch x86_64 runtime.c
```

# Using the Racket x86 interpreters (starting from the Tuples compiler)

This section describes how you can use `racket_interp_x86` and
`racket_interp_pseudo_x86` interpreters defined in the
[`racket_interp_x86.py`](racket_interp_x86.py) file. The x86 interpreter defined
in the [`interp_x86`](interp_x86) directory doesn't support the x86-like
languages generated by the select instructions pass of every compiler starting
from the chapter on tuples. The interpreters in
[`racket_interp_x86.py`](racket_interp_x86.py) will help you interpret these
x86-like languages along with actual x86 code. As the name suggests, these
interpreters run using the x86 interpreter in the Racket version of this
repository.

## Setup instructions

1. Install Racket from [here](https://racket-lang.org/download/).

1. Clone the [Racket version of this
   repository](https://github.com/IUCompilerCourse/public-student-support-code)
   into the **parent directory** of this repository. The directory into which
   you clone the repository is important because `racket_interp_x86.py` is
   hardcoded to look for the Racket version of the x86 interpreter in the parent
   directory.

1. Add `racket_interp_pseudo_x86` interpreter to your `interp_dict` for passes
   before assign homes. For the remaining passes, use `racket_interp_x86`.

## Caveats

* Since your x86 code is interpreted in Racket, any errors occurring during
  interpretation will show up in the output diff and not as a Python exception.
* When implementing the languages up to Ltuple, add the `num_root_spills` field to the
  `X86Program` object. Initialize the field `num_root_spills` to the number
  of tuple variables that have been spilled into the root stack.
* When implementing the languages beginning with Lfun and after,  add the following fields to every `FunctionDef` object:
  - `num_root_spills`: Initialize this field to the number
    of tuple variables that have been spilled into the root stack.
  - `num_params`: Initialize this field to the number of parameters that the function
    had after the limit functions pass but before the select instructions pass.
  

# Type checking (local addition)

This copy of the support code has type hints, checked by mypy.

```
python3.12 -m venv .venv && .venv/bin/pip install mypy   # one-time setup
.venv/bin/mypy .                                         # check everything
.venv/bin/python tools/snapshot.py                       # behavior snapshot
```

- `mypy.ini` lists which modules are fully annotated and checked with the
  `--strict` flags. Everything else gets mypy's default checks.
- `stubs/lark` is a minimal type stub for the vendored lark parser.
- `tools/progress.py` is the chapter 2 scoreboard. It runs every test in
  `tests/var` through the passes in `compiler.py` and checks, after each pass,
  that the output has the right *shape* (`tools/shapes.py`, from the book's
  grammars) and the right *output* (interpreters, and finally real x86 via gcc).
  `-v` shows every failure; `-k text` filters tests by name.
- `tools/progress.py --chapter 4` is the chapter 4 (register allocation)
  scoreboard, for `compiler_register_allocator.py`. It also checks
  uncover_live, build_interference, color_graph and allocate_registers on
  the book's worked examples (figures 4.1-4.6), checks each allocation
  (`tools/regalloc_checks.py`: no reserved registers, interfering variables
  apart, call-live variables out of caller-saved registers, spills below the
  saved registers), and overwrites the caller-saved registers after every
  `callq` when interpreting, the way a real call may.
- `tools/progress.py --chapter 5` is the chapter 5 (Booleans and
  conditionals) scoreboard, for `compiler_conditionals.py`. It runs the
  tests in `tests/if` through shrink, remove_complex_operands,
  explicate_control, select_instructions, assign_homes, patch_instructions
  and prelude_and_conclusion (figure 5.15), checking each output's shape
  (L_If, L_If^mon, C_If, x86_If), type checking the L_If and C_If outputs
  with the book's type checkers, and flagging code that explicate_control
  duplicated. It also checks uncover_live and build_interference on
  multi-block examples (figures 5.12 and 5.14), and that the type checker
  rejects every program in `tests/if_type_errors` (exercise 5.1).
- `tools/make_golden.py` writes the expected output (`.golden`) for new test
  programs (`tests/var` and `tests/if`) by running the definitional
  interpreter.
- `tools/snapshot.py` prints a deterministic report: every module imports,
  each test directory's interpreter and type checker on `tests/` (Lvar, Lif),
  AST printing, the Cif interpreter and type checker on figure 5.12, and the
  x86 interpreter. Diff its output before and after a refactor.
